# 粗选反馈模型：待解决问题与候选方案

> 记录自 session-fa767614（半弦咖啡）。
>
> 状态（0.1.10）：v1 的 like / save-trait 已落到工作台 sidecar `shortlist-likes/1`，并接上 3 张滑动窗和最多 3 张整页短名单。blend 与特征 token 化仍不做。删除 note 不会自动当约束。

## 已观察到的真实问题

1. **“两个都喜欢，但只能留一个待定”**
   - 当前 `shortlist-decisions/1` 每个候选只有 `eliminate` / `defer`，每轮最多 1 个 `defer`。
   - 用户同时喜欢两个方向、且想要“两者之间”时，只能删掉其中一个，或放弃另一个的表达。
2. **“字体很喜欢，但候选被删掉后特征也消失”**
   - 用户在 round 2 的删除理由 note 里写了“万圣节/！字体很好，字体用这个”。
   - note 会落盘，但它是**删除动作的附注**，不是可复用的生成约束；下一轮是否沿用取决于模型是否主动读取和解释。
   - 最终选中的是另一个候选，喜欢的字体没有成为独立资产保留下来。

## 根因

当前模型把“候选”当成不可拆的整体：留 = 整个方向留，删 = 整个方向删。
但用户真正想保留的经常是**局部特征**（字体、配色、版式、图形语言）和**两个方向之间的关系**（更偏向 A 与 B 之间）。

## 候选方案（建议按阶段）

### v1：独立的“喜欢 / 特征”层，不改协议上限

- 每个候选增加两个与删除/待定正交的动作：
  - `like`：可多选，不占 pending，不影响 final 资格。
  - `save-trait`：保存局部特征，例如 `typography` / `palette` / `layout` / `graphic`，附一句自由文本。
- 数据写入 sidecar：`shortlist-likes/1`（与 decisions 分离），不改变 `pending <= 3` 的协议。
- 下一轮生成时，把 `likes` 摘要作为生成上下文注入；被删除候选的字体也可以继续使用。
- UI：候选卡底部增加“喜欢这个方向”“收藏这个字体/配色”两个轻按钮；不需要用户先决定删/留。

### v2：“两者之间 / 合并”作为终选动作

- 终选增加 `choice.kind = "blend"`，`fromPos: [a, b]`，可选权重或一句“更偏向谁”。
- 不要求两个候选都留在 pending；用户可以在任意时刻把两个 liked 候选组成一个 blend。
- 生成器读取 `blend` 和 `likes`，生成一张新的合并稿；最终交付记录来源候选与保留特征。
- 协议上只扩展 choice，不改变 4 轮 × 3 上限；`shortlist-result/1` 增加 `blend` 来源。

### v3：特征 token 化（长期）

- 把字体/配色/版式抽成可命名 token（如 `display-grotesque-heavy`、`vermilion-on-bone`），候选引用 token，生成器按 token 组装。
- 这会把“候选”从整页截图变成可组合的配方，才真正支持“两者之间”。

## 最小可做版本

先做 **v1 的 like + save-trait**：
1. 三栏卡增加“喜欢”和“收藏字体/配色”按钮，允许对已删除候选操作。
2. 服务端写 sidecar，不碰 pending 和 final 协议。
3. 下一轮 preview 的 payload 增加 `likedTraits` 摘要，模型生成时读取。
4. 等真实使用两次后再决定是否做 blend。

这样能先解决“喜欢的特征被删掉”，而不用马上改 12 个上限和终选状态机。
