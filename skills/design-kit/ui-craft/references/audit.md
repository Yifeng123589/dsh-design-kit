# 审阅

何时读我：页面写完、改动完成、上线前；或用户要求「看看这个页面怎么样」「评审一下」「打磨一下」。只审阅不重建时，从这里开始，不要重做方向。

审阅的目标是给出**可执行的结论**，不是打分表演。结论只有四种：通过、修一批、重做某一部分、需要用户决策。

## 1. 顺序

先量化，再视觉，再内容，最后结构。顺序不能反：颜色对比度算错时，讨论「氛围」没有意义。

1. **量化**：`node <skill-dir>/scripts/design-lint.mjs <entry> --json`
2. **视觉**：`node <skill-dir>/scripts/capture.mjs <entry> --out .review`，逐张看
3. **内容**：真实文案、演示数据是否标注、状态是否齐全
4. **结构**：可访问性、语义、键盘路径

## 2. 量化检查（脚本覆盖的部分）

修全部 `error`。`warn` 每条给结论。

| 分组 | 规则 id | 判读 |
|---|---|---|
| AI 味 | `gradient-text` `glass-decoration` `accent-border-bar` `hard-offset-shadow` `kicker-eyebrow` `nested-card` `emoji-icon` `transition-all` `card-grid-uniform` | 不是绝对禁止，是「默认不要用」。简报明确要求或世界本身成立时才保留，并在交付里说明理由 |
| 排版 | `type-scale-flat` `font-family-overload` `body-line-height` `tracking-tight` `body-too-small` | 基本都该修。字号问题优先于颜色问题，因为影响可读性 |
| 色彩 | `contrast-fail` `hardcoded-color` `dark-mode-missing` `focus-invisible` `focus-removed` | `contrast-fail` 一律修；`focus-removed` 一律修 |
| 结构 | `img-alt` `heading-order` `form-label` `html-lang` `reduced-motion` `touch-target` | `img-alt` `heading-order` `form-label` 一律修 |
| 中文 | `cjk-justify` `cjk-break-all` `cjk-mixed-spacing` `cjk-double-punct` `cjk-font-stack` | 前两条改掉；混排间距按需；双标点与字体栈必改 |

脚本没覆盖的，靠下面的清单逐项看。别因为脚本全绿就认为页面没问题。

两个已知盲区，必须人工补：

- **对比度只检查「同一条规则里同时声明 `color` 与 `background`」的组合**，以及内联样式。跨元素继承的背景（例如带底色表格行里的浅灰小字）算不出来，要人工确认。
- **触摸目标只检查能识别出的交互选择器**。类名与业务含义相关时可能漏报，移动端需要人工量一遍。

## 3. 视觉检查

有截图时逐张看，至少两个宽度（如 1440 与 390），加上真实交互态。看这几件事：

- **首屏**：三秒内能否说出这是什么、给谁、下一步做什么。
- **层级**：一屏是否有且只有一个第一眼；去掉颜色后层级是否还成立。
- **溢出与重叠**：长标题、长邮箱、两位数字变五位、系统字号放大后是否还成立。
- **密度**：挤与空是不是由内容决定，而不是由模板决定。
- **状态**：hover / focus / disabled / loading / error / empty 逐个点开。
- **浏览器细节**：选区颜色、焦点环、滚动条、下划线偏移、表格数字对齐。
- **移动端**：触摸目标、软键盘顶起、安全区、横向滚动。

没有截图时（脚本返回 `CAPTURE_UNAVAILABLE`）：明确告诉用户「我在当前环境无法截图，以下判断基于代码与静态检查」，把 `contact-sheet.html` 给对方打开，并把需要对方确认的 3 到 5 件事列清楚。

## 4. 评分表

用于比较或定位问题，不需要每次都填满。每项 1 到 5 分，3 分是「能用但普通」。

| 维度 | 1 到 2 分 | 3 分 | 4 到 5 分 |
|---|---|---|---|
| 方向 | 只有形容词，或照抄品类默认 | 有方向但执行不彻底 | 一句话能说清机制，且页面看得出来 |
| 首屏 | 页头加按钮 | 信息齐全但无记忆点 | 一屏即论点，记得住 |
| 层级 | 所有东西一样重 | 有主次 | 主次分明，去掉颜色也成立 |
| 排版 | 字号随意、行宽失控 | 有阶梯但细节糙 | 阶梯、行高、字距、混排都成立 |
| 色彩 | 默认紫渐变或撒点强调 | 有策略但不彻底 | 策略明确，颜色承担面积 |
| 间距 | 随机值、组内组间不分 | 有基准但不统一 | 节奏清楚，留白有意图 |
| 状态 | 只有默认态 | 有基本状态 | 六态齐全，边界内容成立 |
| 动效 | 满屏相同入场或没有 | 有动效但打断阅读 | 一个作者时刻，可中断、可降级 |
| 文案 | 营销腔、翻译腔 | 通顺但空泛 | 具体、可执行、术语一致 |
| 完成度 | 占位符、断链、无文档 | 能跑但有缺口 | 可上线，有 DESIGN.md 与交付说明 |

## 5. 结论与修复批次

- **通过**：无 error，无关键 warn，视觉检查未发现明显问题。写明「检查了什么」。
- **修一批**：把问题按「一眼可见 → 可读性 → 细节」排序，一次修完同一类，再复检一次。
- **重做某一部分**：只针对某个 section、组件或首屏，不重做整页。
- **需要用户决策**：方向取舍、品牌资产、是否保留某个反常规选择。

修复规则：

1. 成批修复，不要一改一截图。
2. 最多两轮。第二轮结束时，把仍未解决的问题列为已知限制。
3. 不为了指标好看而改设计意图。若规则与已批准方向冲突，保留方向并在交付里说明。
4. 「已经改了很多」不是通过的理由；结论只依据当前状态。

## 6. 审阅报告格式

给用户的报告不超过一屏：

```markdown
## 结论：修一批

### 必修（影响可用性）
- [ ] `styles.css:42` 对比度 3.1:1，正文要求 4.5:1。次级文字改用品牌色相的浅色档。
- [ ] 表单错误只在顶部汇总，未指向具体字段。

### 建议（影响完成度）
- [ ] 空状态只有插画，补一句「这里会有什么」和一个主行动。

### 保留（有意为之）
- 硬偏移阴影：简报要求新粗野主义，保留。

### 未验证
- 移动端 390 宽未截图，需要你在浏览器确认。
```

## 7. 完成前自查

- [ ] `design-lint` 无 `error`，每条 `warn` 有结论
- [ ] 至少两个宽度检查过，或已声明无法检查
- [ ] 交互态逐个点过，或已声明未检查
- [ ] 长内容、空数据、错误、加载四种边界都走过
- [ ] 报告写了「未验证」的部分，没有把推测写成结论
- [ ] 修复最多两轮，剩余问题已列为已知限制
