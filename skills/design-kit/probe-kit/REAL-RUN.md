## 按协议该怎么读

1. **一轮不是证据。** 收敛判定是 `insufficient`，不是 `evidence`。协议要求同向 ≥2 轮，而且 n=1 评审人本身封顶。
2. **输出是区间，不是 37.5%。** 已写的 `ledger/calibration-real-r1.json` 标的是 `[0.25, 0.5]` 区间 + 低置信度归因；37.5% 只是区间中点，不能当结论。
3. **这一轮要按「未完整查看」处理。** 位置 3 停留 1 秒 + 视口偏窄，说明呈现器没有做到「同等显著」。这是协议 P3（呈现面缺失）在真实数据里的直接表现。

```json
{"runId":"r4-demo-1-r2-r3",
 "answer":{"kind":"absolute","chosenPos":2},
 "flips":18,

```

第三轮映射：位置 1=40.6%、位置 2=42.2%、位置 3=39.1%；选中 **42.2%**，18 次改主意，把握 3。

**评审者的原话：「说实话肉眼已经很难看出区别了，设计问题这个是。」**

这句话改变了结论的性质。三轮值 37.5 → 43.75 → 42.2，按数值收窄规则可以判 `evidence`；但第三轮的三个微变体只差 1.5 个百分点，评审者明确报告不可辨。**这是一次低于仪器分辨率（JND）的测量，不能当偏好证据。** 协议的 3.3「区间插值」默认了无限分辨率，没有定义可辨识下限，这是协议本身没覆盖的问题（记为 P11）。

最终写出的校准（`ledger/calibration-real-final.json`）因此是**等效区间**，不是点值：

```
accent_saturation = 42%（默认值）
boundary: kind = jnd-band, lo = 42.2%, hi = 43.75%
          note: 最近两轮差低于可辨识阈值 JND（5%），两者等效；
                默认值取最近一次指认，不主张区间内更细的差异
convergence: evidence · R1 0.375 → R2 0.4375 → R3 0.4219，
             最新一轮与上一轮差 0.0156 在容差内（停在端点）；n=3 轮，弱证据
attribution: assumption「该轴在 39%-44% 区间内对评审者不可辨」
             boundary「等效区间 [37.5%, 43.75%]；低于 JND 的差异不构成偏好证据，停止细分」
```

**怎么消费这个结论：**

- 可以用 **42%（或 38%-44% 内任意值）** 作为默认强调色饱和度；不要声称「用户精确偏好 42.2%」。
- 不要再做第四轮。三轮已经把轴压到可辨阈值以内，继续细分只会得到噪声，且 `maxRuns` 已用满。
- 如果之后真实使用中这个默认值反复被手改，那才是新的证据（预算法），触发下一轮而不是靠再加插值。

## 协议层面的新问题（P11）

> **可辨识阈值（JND）未定义。** 3.3 区间插值假设评审者能分辨任意小的差异；真实仪器（屏幕、字体渲染、人眼）有分辨率下限。低于 JND 的「指认」是噪声，不是偏好，把它当数据会系统性高估收敛。

工具侧的修法（已实现）：

1. 轴声明 `jnd`（R4 实测 5 个百分点）。
2. `build --between` 在区间窄于 `2 × JND` 时**拒绝细分**（退出码 2），除非 `--force`；报错直接建议「结论写成区间内等效/不敏感」。
3. 差异低于 JND 的两轮判为「同一档」并给出 `jndBand`；`apply` 把边界写成 `jnd-band`，不写点值。
4. `review` 显示「轴分辨率 JND」与「同档提示」，避免把不可辨差异读成偏好移动。

## 工具侧要修的两件事（第一轮暴露）

1. **窄视口下的呈现器不合格。** 3 列固定 360px 在 <1120px 视口下不能同屏，直接影响指认质量。已修：窄屏时显示琥珀色告警「只能同屏看到约 N / 3 个变体，请先滚动看全」。变体渲染尺寸与顺序未变。
2. **第一条记录早于 `answer.env` 落账。** 现在 `makeRunEvent` 会把指认时的 `viewport/lang/reducedMotion` 记进 `answer.env`，`review` 会提示视口偏窄；第一轮的信息只存在于 `ledger/answers/real-r4-demo-1.jsonl`。
